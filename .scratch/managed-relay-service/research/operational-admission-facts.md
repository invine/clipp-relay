# Operational admission facts

Research date: 2026-09-07. Supports [remaining operational Safety Limits](../issues/16-define-remaining-operational-limit-defaults.md), supplementing [initial-limit evidence](initial-limit-evidence.md). Inspected the installed module-cache source for **go-libp2p v0.49.0** and its pinned memory dependency; tagged upstream links identify the same source paths. No benchmark, installation or production implementation was performed. Numeric defaults below describe upstream, not selected relay policy.

## Resource Manager scopes are intersecting ceilings

- The manager enforces a graph of scopes, not a queue or fairness scheduler. A resource request can fail at any applicable scope. System is global; transient covers connections before peer assignment and streams before protocol assignment. After assignment, connection resources move from transient to peer/system; stream resources move to peer/protocol/system and then additionally service/service-peer. Protocol-peer limits also apply. An application-authenticated Relay Session is not a built-in scope: libp2p peer authentication occurs earlier. [Scope model](https://github.com/libp2p/go-libp2p/blob/v0.49.0/p2p/host/resource-manager/README.md), [assignment implementation](https://github.com/libp2p/go-libp2p/blob/v0.49.0/p2p/host/resource-manager/rcmgr.go#L784-L966).
- Connection and stream limits have inbound, outbound and combined dimensions. Service/protocol budgets constrain attributed streams and reserved memory, not all transport connections merely because the process is a relay. A high global limit cannot override a lower peer, protocol, service or directional limit. Explicit limits must cover all relevant dimensions and retain headroom for identify, authentication, reservation renewal and teardown/control traffic. This headroom requirement is an engineering inference from the shared scopes. [Resource definitions](https://github.com/libp2p/go-libp2p/blob/v0.49.0/p2p/host/resource-manager/limit_defaults.go), [scope implementation](https://github.com/libp2p/go-libp2p/blob/v0.49.0/p2p/host/resource-manager/scope.go).
- Memory accounting covers reservations made by cooperating components; it is not a process-RSS, kernel-memory or Go-heap limiter. Connection FD accounting depends on the transport's `usefd` flag: TCP/WebSocket use true; WebRTC uses false with shared UDP transport infrastructure. Therefore FD totals are not simply session counts, and unaccounted process resources still need operating-system/container budgets. [Manager resource model](https://github.com/libp2p/go-libp2p/blob/v0.49.0/p2p/host/resource-manager/README.md), [TCP](https://github.com/libp2p/go-libp2p/blob/v0.49.0/p2p/transport/tcp/tcp.go#L255), [WebRTC](https://github.com/libp2p/go-libp2p/blob/v0.49.0/p2p/transport/webrtc/listener.go#L167).
- Allowlisted addresses can use separate system/transient limits when normal limits reject them. An absolute whole-process admission budget must account for that escape path or avoid adding allowlist capacity. This is not the portal administrator allowlist. [Allowlist fallback](https://github.com/libp2p/go-libp2p/blob/v0.49.0/p2p/host/resource-manager/rcmgr.go#L383-L419).

## Automatic scaling is not Pod-aware sizing

`AutoScale()` uses total memory divided by eight and the process's soft `RLIMIT_NOFILE` divided by two. The pinned Linux memory library calls `syscall.Sysinfo`, without reading cgroup memory limits. **Inference:** do not assume the resulting memory budget follows the Pod limit on OCI; resolve explicit budgets from the deployment contract instead. Using a fixed limiter is supported, but unspecified fields still inherit whatever defaults were used to build it. This lookup deliberately does not derive final memory or FD numbers. [Scaling code](https://github.com/libp2p/go-libp2p/blob/v0.49.0/p2p/host/resource-manager/limit_defaults.go#L629-L634), [FD discovery](https://github.com/libp2p/go-libp2p/blob/v0.49.0/p2p/host/resource-manager/sys_unix.go), [pinned memory implementation](https://github.com/pbnjay/memory/blob/7b4eea64cf58/memory_linux.go).

## A relayed circuit consumes two relay-facing streams

- The source opens inbound HOP; the relay opens outbound STOP to the destination over an existing connection (`WithNoDial`). Both streams attach to the relay service. A successfully active circuit therefore occupies one inbound HOP plus one outbound STOP in the relay process: two system/service streams, one in each endpoint's peer/service-peer scope. HOP reservation/control requests also consume streams while being handled. Endpoint application streams inside the encrypted circuit are not separately visible as relay-host streams. [HOP handler](https://github.com/libp2p/go-libp2p/blob/v0.49.0/p2p/protocol/circuitv2/relay/relay.go#L137-L165), [STOP creation](https://github.com/libp2p/go-libp2p/blob/v0.49.0/p2p/protocol/circuitv2/relay/relay.go#L359-L405).
- HOP and STOP have separate protocol limits as well as the shared relay service limit. Upstream base relay service capacity is 256 **combined** streams, despite each directional field also being 256; service-peer base is 64 combined. Consequently “256 streams” is not “256 simultaneous circuits,” and counting circuit slots without transient control headroom can starve reservations. The exact final capacity must also pass endpoint circuit caps and other scopes. [Default service/protocol limits](https://github.com/libp2p/go-libp2p/blob/v0.49.0/limits.go#L78-L106), [endpoint circuit checks](https://github.com/libp2p/go-libp2p/blob/v0.49.0/p2p/protocol/circuitv2/relay/relay.go#L302-L342).

## Admission versus trimming existing connections

The default connection manager uses low/high watermarks 160/192. Its ordinary trimming skips explicitly protected peers, but application authentication alone does not protect one. `Protect` is peer-wide, not specific to one account-authenticated transport connection. `ForceTrim` may close protected peers too. **Policy implication, not selection:** if admitted authenticated idle sessions must survive ordinary overload, explicitly prevent opportunistic trimming (for example a no-trim manager plus hard admission control), or define protection/lifecycle rules and emergency exceptions. Raising Resource Manager limits alone does not change this behavior. [Default manager](https://github.com/libp2p/go-libp2p/blob/v0.49.0/defaults.go#L120-L128), [ordinary/emergency trimming](https://github.com/libp2p/go-libp2p/blob/v0.49.0/p2p/net/connmgr/connmgr.go#L153-L178), [protected-peer handling](https://github.com/libp2p/go-libp2p/blob/v0.49.0/p2p/net/connmgr/connmgr.go#L460-L510).

## Public transport handshake boundaries

- `ConnectionGater` offers acceptance, secured-peer and upgraded-connection checkpoints. It has no Relay Account identity at raw acceptance and is not itself a handshake timeout or byte limiter. Each transport's actual hook placement matters. The application needs a distinct post-libp2p/pre-relay-authentication deadline/count: transient connection accounting ends at peer assignment, not account authentication. [Gater interface](https://github.com/libp2p/go-libp2p/blob/v0.49.0/core/connmgr/gater.go), [peer scope transfer](https://github.com/libp2p/go-libp2p/blob/v0.49.0/p2p/host/resource-manager/rcmgr.go#L784-L844).
- TCP's gated listener checks acceptance and opens a Resource Manager connection scope before the secure/mux upgrade. The common upgrader has a 15-second default accept timeout and a `WithAcceptTimeout` constructor option; wiring a custom value through host construction must be verified rather than assumed to be a top-level relay option. [Listener](https://github.com/libp2p/go-libp2p/blob/v0.49.0/p2p/net/upgrader/listener.go), [upgrader options](https://github.com/libp2p/go-libp2p/blob/v0.49.0/p2p/net/upgrader/upgrader.go#L28-L41).
- In this pinned WebSocket implementation, the HTTP listener is already a gated/accounted listener before TLS/HTTP upgrade. Its negotiating connection has a handshake timeout; `WithHandshakeTimeout` is exposed. Therefore it is incorrect to claim all WSS handshake sockets bypass Resource Manager. External ingress/proxy resources, kernel accepts and optional non-WebSocket HTTP-handler traffic still require their own accounting/deadline review. [WebSocket listener](https://github.com/libp2p/go-libp2p/blob/v0.49.0/p2p/transport/websocket/listener.go#L68-L135), [negotiation lifetime](https://github.com/libp2p/go-libp2p/blob/v0.49.0/p2p/transport/websocket/listener.go#L320-L370), [option](https://github.com/libp2p/go-libp2p/blob/v0.49.0/p2p/transport/websocket/websocket.go#L80-L90).
- WebRTC Direct uses a 128-slot in-flight semaphore, a fixed 10-second candidate setup timeout, and gating/resource scope before expensive peer-connection setup. UDP/STUN demultiplexing precedes that gate. The apparent `WithListenerMaxInFlightConnections` helper exists only in `_test.go`, not the production API. Do not promise arbitrary configuration of those upstream constants without an integration seam or upstream change. Explicit transient limits can impose a lower shared cap after Resource Manager entry. [Listener](https://github.com/libp2p/go-libp2p/blob/v0.49.0/p2p/transport/webrtc/listener.go#L37-L180), [test-only option](https://github.com/libp2p/go-libp2p/blob/v0.49.0/p2p/transport/webrtc/transport_test.go#L339-L348).

## Additional defaults that must not remain hidden

Resource Manager independently installs IP/subnet concurrent-connection and rate limiters, separate from relay reservation IP/ASN restrictions. Defaults include eight concurrent connections per IPv4 /32 and an IPv4 /32 rate of 0.2 requests/second with burst 16; IPv6 has subnet rules. Loopback has exceptions. These remain active when only fixed scope limits are raised. Explicitly reconcile them with shared-proxy/CGNAT behavior and the accepted IP-throttling policy; do not silently introduce a second admission policy. The source provides customization options, whose chosen configuration still needs testing. [Constructor](https://github.com/libp2p/go-libp2p/blob/v0.49.0/p2p/host/resource-manager/rcmgr.go#L145-L160), [concurrency limits](https://github.com/libp2p/go-libp2p/blob/v0.49.0/p2p/host/resource-manager/conn_limiter.go#L33-L104), [rate limits](https://github.com/libp2p/go-libp2p/blob/v0.49.0/p2p/host/resource-manager/conn_rate_limiter.go).

No source here demonstrates sustainable 5,000-session capacity, attack-resistant fairness or bounded total RSS. Next choices can independently settle admission counts, application-authentication deadlines and overload behavior; final memory/FD budgets and transport stress acceptance remain a separate derivation and measurement gate.
