# PostgreSQL backup tool options

Research date: 2026-09-07. Supports [the recovery frontier](../issues/15-define-postgresql-backup-restore-and-deletion-recovery.md). This is factual planning research, not an accepted tool choice or a tested deployment. Scope: bundled PostgreSQL 18, Debian/ARM64, OCI Object Storage, encrypted physical backups and WAL/PITR, bounded retention.

## Candidate: pgBackRest

- Upstream explicitly added PostgreSQL 18 support in 2.55.0. Debian Trixie packages pgBackRest 2.55.1 for ARM64 as well as AMD64; this establishes package availability, not that the official PostgreSQL container already contains it or that an arbitrary copied executable has all required libraries. [Release history](https://pgbackrest.org/release.html), [Debian package](https://packages.debian.org/trixie/database/pgbackrest).
- pgBackRest documents full, differential and incremental backups, WAL archiving, PITR, and S3-compatible repositories. The repository bucket must already exist. These fit an operator-provided bucket and a database-aware backup workflow. [User guide](https://pgbackrest.org/user-guide.html).
- Its configuration supports custom S3 endpoints and client-side AES-256-CBC repository encryption; encryption is not enabled by default. Expiring a full backup removes dependent differential/incremental backups; default WAL retention follows retained full backups. Aggressively shortening WAL retention can remove PITR coverage. [Configuration reference](https://pgbackrest.org/configuration.html).

## Alternative: WAL-G

- WAL-G documents PostgreSQL base/delta backup push/fetch and WAL push/fetch for archive and restore commands. Its PostgreSQL documentation also describes WAL integrity checks. These are the necessary building blocks for PITR, not proof of a particular RPO/RTO. [PostgreSQL documentation](https://github.com/wal-g/wal-g/blob/master/docs/PostgreSQL.md).
- The v3.0.9 release provides PostgreSQL binaries for Ubuntu 22.04/24.04 on AArch64 and AMD64. That is not a verified Debian Trixie compatibility guarantee. This bounded lookup did not establish explicit PostgreSQL 18 certification for that exact release. [Release assets](https://github.com/wal-g/wal-g/releases/expanded_assets/v3.0.9).
- Its S3 backend accepts a custom endpoint, region, access/secret key and path-style addressing, so the documented OCI route is S3 compatibility rather than a verified native OCI integration. [Storage documentation](https://github.com/wal-g/wal-g/blob/master/docs/STORAGES.md).
- WAL-G documents optional OpenPGP and libsodium client-side encryption. Libsodium support is build-dependent. Deletion is dry-run unless confirmed; `retain FULL` retains full-backup chains, and `before FIND_FULL` preserves the necessary full backup for dependent deltas. Permanent backups bypass ordinary cleanup. Thus chain-aware cleanup exists, but its configuration and encryption capabilities must be checked against the pinned binary. [General documentation](https://github.com/wal-g/wal-g/blob/master/docs/README.md).
- Current PostgreSQL documentation warns that default timeline/WAL ordering can misorder backups across a major upgrade, and discusses separate prefixes and sentinel-time ordering. These are current-branch docs; exact release availability must be verified before depending on those options. [PostgreSQL documentation](https://github.com/wal-g/wal-g/blob/master/docs/PostgreSQL.md).

## OCI interoperability and encryption boundary

- OCI exposes an S3-compatible API with namespace/region-specific endpoints and Customer Secret Keys. Both tools have the matching configurable S3 client surface. **Inference:** pgBackRest is a practical first candidate for an OCI integration test, not an end-to-end compatibility claim from either vendor. [OCI S3-compatible API](https://docs.oracle.com/en-us/iaas/Content/Object/Tasks/s3compatibleapi.htm), [pgBackRest guide](https://pgbackrest.org/user-guide.html), [WAL-G storage documentation](https://github.com/wal-g/wal-g/blob/master/docs/STORAGES.md).
- Do not assume AWS-specific KMS, object-lock or version-recovery features work unchanged through OCI's compatibility API. Tool-level encryption needs an independently recoverable decryption secret; retaining encrypted objects without the necessary key cannot satisfy recovery. The key custody and rotation contract remains a deployment/recovery design decision, not something S3 endpoint selection resolves. [OCI compatibility API](https://docs.oracle.com/en-us/iaas/Content/Object/Tasks/s3compatibleapi.htm), [pgBackRest encryption options](https://pgbackrest.org/configuration.html), [WAL-G encryption options](https://github.com/wal-g/wal-g/blob/master/docs/README.md).

## Maximum 30 days is not a built-in retention guarantee

- pgBackRest `repo-retention-full-type=time` protects a recovery window rather than enforcing maximum object age: its documented example retains a 35-day-old full backup when the other full backup is only 25 days old and retention is 30 days. Historical manifests have separate retention and default to no expiry. Neither setting should silently be equated with “nothing older than 30 days exists.” [Configuration reference](https://pgbackrest.org/configuration.html).
- OCI lifecycle execution is explicitly **best-effort**: the note near the beginning says execution can take longer than normal, even much longer in unusual circumstances. Its “Working with Object Lifecycle Management Policies” section says age uses last modification time rounded up to a UTC day and evaluation runs daily. This is direct evidence against promising hard physical erasure exactly at day 30. [OCI lifecycle documentation](https://docs.oracle.com/en-us/iaas/Content/Object/Tasks/usinglifecyclepolicies.htm).
- Current objects, previous versions and uncommitted multipart uploads are distinct lifecycle targets. A complete cleanup policy must account for all relevant targets and permissions; expiring the active backup alone is not evidence that every stored copy was removed. [OCI lifecycle documentation](https://docs.oracle.com/en-us/iaas/Content/Object/Tasks/usinglifecyclepolicies.htm).
- OCI retention rules impose a **minimum** no-modification/no-deletion period; they do not automatically delete objects afterwards. Locked rules cannot be shortened, and active protection prevents lifecycle deletion. OCI also constrains combining retention rules with bucket versioning. **Inference:** bucket-wide immutable retention can conflict with any backup metadata the tool must overwrite and with a maximum-age cleanup policy. Do not enable it on a live repository without checking that interaction. [OCI retention rules](https://docs.oracle.com/en-us/iaas/Content/Object/Tasks/usingretentionrules.htm).

## Recommendation and remaining verification

**Engineering recommendation, not policy:** evaluate pgBackRest first because this lookup found explicit PostgreSQL 18 support, a Debian ARM64 package and integrated chain-aware backup/WAL management. WAL-G remains a credible alternative, but its exact PostgreSQL 18/Debian/encryption release combination needs more verification.

Before selecting either tool, test the pinned build in the hardened non-root container, required filesystem/database privileges, OCI upload/list/download/delete and multipart behavior, encrypted base-plus-WAL recovery, failure/retry behavior, private logging, chain-safe expiry and observed recovery times. No such installation, build, cluster operation or integration test was performed here.

**Policy clarification needed:** does the accepted maximum 30 days mean backup restore eligibility ends and purge is initiated by the deadline, with monitored provider deletion completion, or a hard physical erasure deadline? These are materially different promises. OCI lifecycle alone does not establish the latter. Do not reinterpret the accepted maximum as a guaranteed minimum 30-day PITR window, nor let chain-preserving tool defaults silently extend it.
