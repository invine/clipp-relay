# Recovery Journal storage facts

Research date: 2026-09-07. Bounded support for [the recovery frontier](../issues/15-define-postgresql-backup-restore-and-deletion-recovery.md); factual feasibility only, not an implementation or revised policy. No cluster access, installations or builds performed.

## Native OCI object operations

- Native `PutObject` exposes `IfNoneMatch: "*"`: creation fails if the named object already exists. `IfMatch` conditions a replacement on the existing object's ETag. The Go SDK exposes these fields and the response ETag. These provide per-object create-only and optimistic replacement primitives, not a transaction spanning PostgreSQL and multiple objects. [OCI Go Object Storage SDK](https://docs.oracle.com/en-us/iaas/tools/go/latest/objectstorage/index.html#PutObjectRequest), [explicit conditional-request descriptions](https://docs.oracle.com/en-us/iaas/tools/java/3.68.0/com/oracle/bmc/objectstorage/requests/PutObjectRequest.Builder.html).
- OCI documents strong consistency: reads return the latest data written. `ListObjects` is paginated, returns at most 1,000 objects, and uses `nextStartWith` for continuation. **Limit of this lookup:** the reviewed sources do not establish that a sequence of list pages is one atomic snapshot during concurrent writes. A complete recovery scan must not silently treat one page, or a successful empty list, as proof that every historical event exists. [Consistency guarantee](https://docs.oracle.com/en-us/iaas/Content/Object/Concepts/objectstorageoverview.htm), [ListObjects contract](https://docs.oracle.com/en-us/iaas/tools/go/latest/objectstorage/index.html#ObjectStorageClient.ListObjects).
- **Engineering inference:** a timed-out create may have succeeded remotely. Retrying a stable event name and verifying existing content can resolve that ambiguity; treating every already-exists response as successful would miss a conflicting payload. This is application protocol work, not something an ETag alone establishes.

## IAM separation and scope

- `PutObject` requires `OBJECT_CREATE` for a new name and `OBJECT_OVERWRITE` for an existing name. Deletion and version deletion require separate permissions. `GetObject` needs `OBJECT_READ`; listing needs `OBJECT_INSPECT`. Multipart upload requires both create and overwrite privileges, so small single-request journal records avoid that unnecessary expansion. [IAM API/permission table](https://docs.oracle.com/en-us/iaas/Content/Identity/Reference/objectstoragepolicyreference.htm).
- Policies can constrain bucket and object-name patterns. Oracle gives an explicit create-only, no-read/no-delete prefix example. This supports separating an append-only live writer from recovery readers and a controlled cleanup identity. Any additional inherited grant must still be audited; the restricted statement does not cancel a broader grant. [Object-level IAM examples](https://docs.oracle.com/en-us/iaas/Content/Object/Tasks/managingobjects.htm), [IAM reference](https://docs.oracle.com/en-us/iaas/Content/Identity/Reference/objectstoragepolicyreference.htm).
- Prefix restrictions do **not** prevent listing all object names in the containing bucket. A dedicated journal bucket provides a simpler name-disclosure boundary than sharing a bucket and assuming list filtering is authorization. Object names should themselves omit private account information. [Oracle security guidance](https://docs.oracle.com/en-us/iaas/Content/Security/Reference/objectstorage_security.htm).
- **Engineering inference:** a mutable journal head/checkpoint would require overwrite authority for that exact object, distinct from create-only event records. Whether a head, sequence, checkpoint or another completeness mechanism is needed remains an application design decision; these storage capabilities do not select it.

## Authentication without long-lived S3 keys

- Native OCI access can use OKE workload identity with the Go SDK (v65.32.0 onward); Oracle provides an Object Storage upload example. IAM can identify cluster, namespace and Kubernetes service account. This feature requires an **enhanced OKE cluster**, not merely Kubernetes hosted in OCI. Oracle recommends reusing one identity-provider instance for cached tokens. No S3 Customer Secret Key is needed for this native SDK path. [Workload identity requirements and example](https://docs.oracle.com/en-us/iaas/Content/ContEng/Tasks/contenggrantingworkloadaccesstoresources.htm).
- OCI instance principals are another native option: instance certificates are automatically provisioned and rotated, avoiding manually distributed user credentials. The authority belongs to the compute instance; it is not the same isolation boundary as a Kubernetes service account. The cluster type and permitted authentication mode must therefore be confirmed, rather than assumed. [Calling services from an instance](https://docs.oracle.com/en-us/iaas/Content/Identity/Tasks/callingservicesfrominstances.htm).
- This native-journal path does not establish that pgBackRest's S3 backend can reuse the same authentication mechanism. The previously researched backup-tool path and the journal's OCI SDK client are distinct integrations.

## What the API does not prove

The following are engineering limitations/inferences, not additional OCI guarantees:

- Strong consistency tells a reader what currently exists; it cannot prove that privileged deletion, bucket replacement, a wrong prefix, or coherent rollback of the entire journal never occurred.
- Create-only permission protects against that writer overwriting existing records. It does not stop a differently privileged operator or lifecycle authority from removing them, nor prevent a compromised writer from creating false records.
- Per-object conditions do not atomically commit a deletion in PostgreSQL and its journal entry, establish cross-object ordering, or resolve whether an acknowledged deletion is missing after restore. Acknowledgement ordering, retry identity, validation/fencing and any independent completeness anchor remain application responsibilities.
- Checksums or authenticated encryption can detect corrupt/altered bytes under their trust assumptions; they do not by themselves prove that no complete valid record, or entire suffix of valid records, was removed. Operator authority and cleanup scope must be explicit in the recovery threat model.

## pgBackRest integration with the official PostgreSQL image

- PostgreSQL executes `archive_command` as its server OS user. pgBackRest's documented setting invokes local `pgbackrest ... archive-push %p`; that executable must actually be runnable with its dependencies and configuration where PostgreSQL executes the command. Merely putting a backup Job elsewhere does not supply it. [PostgreSQL archiving contract](https://www.postgresql.org/docs/18/continuous-archiving.html), [pgBackRest guide](https://pgbackrest.org/user-guide.html).
- A dedicated remote repository host still requires pgBackRest on the PostgreSQL host, with exactly matching local/remote versions; the guide describes SSH or TLS transport between them. Remote backup is not a SQL-only client that eliminates the database-side helper. [Dedicated repository host documentation](https://pgbackrest.org/user-guide.html).
- The reviewed official PostgreSQL 18/Trixie Dockerfile does not install pgBackRest. **Packaging inference:** preserve the official base but explicitly supply a compatible pgBackRest executable and runtime libraries/configuration, or design and verify a different local-helper arrangement. An executable copied from a different image is not automatically ABI-compatible. The hardened non-root packaging choice is still untested and unresolved here. [Official image source](https://github.com/docker-library/postgres/blob/master/18/trixie/Dockerfile).
