# Define single-process relay control protocols

Type: grilling
Status: resolved
Blocked by: 01, 03, 04

## Question

What versioned wire contracts, trust boundaries, validation rules, error semantics, timeouts, and compatibility behavior should govern Relay Authentication, discovery of the sole current Relay Instance, exact Rendezvous, and the existing Circuit Relay v2 interaction within the single-process v1?

## Answer

Clipp maintains multiple independent Relay Configurations and connects to every configured relay with bounded parallelism, independent status, and independent retry backoff. An authenticated configuration owns credentials scoped to one exact canonical HTTPS Relay Discovery Endpoint; an unauthenticated configuration supplies explicit relay multiaddrs. Authenticated configurations never fall back or downgrade to unauthenticated operation, and credentials are never sent to another relay service.

The authenticated service exposes `GET /v1/relay`. It requires `Authorization: Bearer <token>`, rejects redirects, and returns `{"version":1,"relay":{"peerId":"...","addresses":["..."]},"validUntil":"...Z"}` to any active Relay Account with the discovery scope. Relay Authentication, rather than discovery, performs authoritative Relay Quota and session admission. All returned addresses are complete, form an unordered set, and contain the declared process-lifetime Peer ID. Clients atomically reject malformed, expired, or unsupported documents; ignore valid addresses for unsupported transports; try every supported address; and refresh at `validUntil`, after Peer-ID mismatch, or after every advertised supported address fails. Document expiry does not invalidate an existing authenticated connection.

Relay Authentication uses `/clipp/relay-auth/1.0.0` with one bounded varint-length-delimited JSON request and response per stream. The request is `{"accessToken":"..."}` and success is `{"ok":true,"sessionExpiresAt":"...Z","renewAfterMillis":...}`. Clipp sends the token only after Noise proves the remote Peer ID equals the authenticated discovery result. Every physical connection independently crosses the Relay Authentication Barrier before HOP or Rendezvous; authentication is never inherited between connections. A Relay Session expires at the earlier of token expiry and the configured maximum and closes the complete connection. Same-account reauthentication may extend it. A failed renewal preserves the old deadline, while failed initial authentication returns one error and closes the connection. A different account cannot replace the association on the same connection; successful authentication on a new connection atomically supersedes older same-Peer-ID connections associated with another Relay Account.

Before Relay Authentication, an authenticated relay exposes only transport establishment, Identify, Ping, and Relay Authentication. Circuit Relay v2 remains wire-compatible and otherwise unmodified: missing, expired, or inactive authentication maps to `PERMISSION_DENIED`, exhausted Relay Quota maps to `RESOURCE_LIMIT_EXCEEDED`, and all stock reservation and Safety Limit statuses remain unchanged.

Authenticated relays preserve exact `/clipp/rendezvous/1.0.0` compatibility and add framed `/clipp/rendezvous/2.0.0`. Clients negotiate v2 first and fall back to v1 only when multistream negotiation reports v2 unsupported. V2 retains fixed-topic `clipp` `register`, `lookup`, and `unregister` operations and encodes Signed Peer Records as unpadded base64url. Registration requires an active Relay Session and live reservation, verifies the envelope signature and subject against the authenticated remote Peer ID, requires at least one circuit address through the current Relay Instance, and stores the envelope unchanged. The Rendezvous Lease ends at the earliest of reservation expiry, Relay Session expiry, or configured Rendezvous TTL. The newest valid registration owns the lease, and cleanup from an older connection cannot delete its replacement. Any active Relay Session may perform an exact-Peer-ID lookup across Relay Accounts; there is no listing, and missing, expired, and unregistered records all return `{"ok":true}` without a record.

Clipp-owned protocols use UTF-8 JSON with unique keys, strict bounded requests, no trailing frames, omitted optional fields instead of `null`, UTC RFC3339 timestamps ending in `Z`, decimal millisecond integers, and no compression. Clients ignore additive unknown response fields but reject unsupported major versions. Valid semantic failures receive one `{"ok":false,"code":"...","retryAfterMillis":...}` frame followed by orderly close; invalid framing, oversize, extra frames, or write timeout resets the stream. The stable initial error registry is `invalid_request`, `authentication_failed`, `account_change_requires_new_connection`, `quota_exhausted`, `session_limit_exceeded`, `reservation_required`, `invalid_peer_record`, `rate_limited`, `temporarily_unavailable`, and `unsupported_version`. Unknown errors fail closed and receive fast automatic retry only with an explicit retry hint or known retryable classification.

Discovery success is HTTP `200`; `invalid_request` is `400`, `authentication_failed` is `401`, `rate_limited` is `429`, and `temporarily_unavailable` is `503`. Responses use JSON and `Cache-Control: no-store`; HTTP `Retry-After` agrees with JSON `retryAfterMillis`. Discovery, transport dialing, Relay Authentication, reservation, and Rendezvous use independent configurable deadlines, with bounded server reads and writes. Numeric defaults belong to the limits ticket, and removal of Rendezvous v1 belongs to the runtime migration decision.
