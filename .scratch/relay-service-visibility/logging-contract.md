# Relay structured logging contract

Status: accepted contract, 2026-10-11 — implementation pending

The [fixed logging catalog](logging-catalog.json) defines operation/outcome/reason
pairs and permitted dimensions. [Prototype the structured logging contract](issues/02-prototype-the-signal-contract.md#answer)
records the human review and the durable prototype branch. This is the accepted
logging decision, not a production implementation or deployed measurement.

## Event rows

| Field | Contract |
| --- | --- |
| `time` | UTC RFC 3339 timestamp generated by the service. |
| `level` | `INFO`, `WARN`, or `ERROR`, chosen from the fixed event classification. |
| `msg` | Static human wording owned by the event catalog; never caller-supplied text. |
| `event` | A fixed event name in the catalog, or the fixed `observation.state`, `observation.threshold` or `log.suppressed` control event. |
| `outcome` | Only the catalog pairs permit `started`, `success`, `refused`, `failed`, `uncertain`, `recovered`, or `ended`; the observation and loss-summary control events may also use `observed`. |
| `reason` | The catalog's fixed safe category; `none` for an ordinary success. Never an exception message or upstream response. |
| `request_id` | Optional 128-bit CSPRNG value rendered as 32 lowercase hex characters, generated separately for each admitted HTTP/protocol request. Never accepted from request headers or derived from credentials. |
| `session_id` | Optional separate 128-bit random value for one admitted physical relay connection. Lives only until that connection ends. Not a Portal Session credential or ID. |
| `transport` | Optional `tcp`, `wss`, `webrtc_direct`, or `unknown`, only when the producer can supply the observation. |
| `client_type` | Optional `electron`, `android`, `extension`, or `unknown`, derived only from a validated registered client or a fixed unknown category. |
| `gate` | Optional fixed admission gate in `public_http,private_http,db_work,provider_work,pending_connection,handshake,session,reservation,circuit,stream,deletion`. Never a caller-selected name. |
| `schema_revision` | Optional nonnegative integer in startup events, preserving the existing safe revision field. |
| `duration_ms` | Optional nonnegative elapsed duration measured by the service. No latency is invented for an aggregate callback without timing evidence. |
| `signal`, `state` | Only for observation transitions; fixed signal/state enums described below. |
| `rate_limited_count`, `queue_full_count`, `window_seconds` | Only for a bounded aggregate diagnostic-loss summary. No request/session identifier list. |

Absent fields are omitted. Correlation IDs never enter durable storage or cross-request lookup tables. Callback requests get new request IDs;
OAuth state and cookies do not provide cross-redirect correlation. If a diagnostic
ID cannot be generated, omit it and count the diagnostic failure without changing
the authorized business outcome. Protocol callbacks with only aggregate evidence
never invent correlation or transport. All fields have typed finite rendering;
NaN, infinity, arbitrary strings, arbitrary JSON and caller-added attributes are
not accepted by the event interface.

INFO covers meaningful successful activity and expected credential, quota,
session and per-request Safety Limit refusals. WARN covers dependency failures,
stale observations, global overload, unconfirmed commits and unsuccessful drains.
ERROR covers fatal startup/listener failures and broken invariants. Fixed
classification distinguishes per-request `safety_limit` from global `overloaded`.
Routine successful DB/provider operations do not produce individual rows; stdout records their failures and state recovery.

Successful routine page/asset requests and periodic stdout status are excluded.
All meaningful initial, changed and recovered lifecycle/observation states are
eligible for logging; an unchanged observation produces no recurring row.

## Output bounds

- Activity token bucket: 20 records/sec, burst 40. Per static catalog tuple
  `(event, outcome, reason, transport, client_type)`: 1 record/sec, burst 5.
- Lifecycle/observation transitions, ERROR and loss summaries use a separate
  reserved bucket: 4 records/sec, burst 8. They are still bounded and can be lost.
- One stdout writer and one non-blocking 256-record queue. Each rendered record
  is at most 2 KiB; queue payload is at most 512 KiB, with metadata bounded by its
  fixed number of slots. Producers never block on stdout or create replacement
  writer goroutines. No log file, secondary logger or retry queue.
- Aggregate loss summary at most once per 10 seconds, and only when loss occurred.
  It contains separate rate and queue counts. It uses the reserved budget;
  Loss counters are held only in bounded process-local logger state until a best-effort summary can report them. They are not exposed as traffic metrics.
- Shutdown allows at most 100 ms for best-effort flushing. Fatal/output loss can
  prevent a row from appearing if stdout is blocked; diagnostics must not hold
  the serving or shutdown path indefinitely.
- The logger records suppressed/dropped row counts in fixed process-local state for loss summaries. Bounded logs omit some individual outcomes and correlation, and process loss can erase a pending summary. No exact traffic-frequency store or claim of a complete event history is introduced.

These are accepted initial budgets, not evidence from a load qualification.

## Scope of this contract

The human narrowed this effort to structured logging on 2026-10-11. New metric
families, changes to the existing private metric endpoint, metric snapshots for
scrapes and collector integration are outside scope. The accepted full
observability ticket retains those requirements for later work. Logs contain no
periodic aggregate traffic/resource dashboard or Prometheus exposition.

The catalog is a logging allowlist, including its finite rate-limit keys. Loss
counts are internal logger bookkeeping used only for `log.suppressed` rows.
They do not provide durable or exact outcome-frequency measurements. Numeric
`duration_ms` describes the individual logged operation, not a histogram.

## Observation states and freshness

Fixed `signal` values: `cleanup,pending_deletion,quota_clock,process_cpu,
process_memory,recovery,full_backup,repository_retention,certificate,
database_resources`.

| State | Meaning and value behavior |
| --- | --- |
| `unknown` | A configured producer has not yet yielded a valid observation. Omit value and last-success timestamp. |
| `unavailable` | No supported/connected producer exists. Omit numeric value; do not report healthy. |
| `available` | A valid current observation exists. Keep the observation valid in memory; the log transition carries only its fixed state/reason, not a periodic gauge row. |
| `failed` | The latest attempted sample failed. Invalidate the current value; preserve an earlier last-success timestamp internally for freshness. |
| `stale` | No valid sample within the permitted freshness interval. Invalidate the current value; preserve its timestamp internally for freshness. |

Existing maintenance diagnostic observations are sampled every 60 seconds, one pass at a time, with a
5-second deadline. A valid sample expires after 180 seconds; a failed attempt
invalidates it immediately. Diagnostic availability does not prove infrastructure health. The quota clock retains its existing stricter safety timing and semantics; the new
sampler must not extend its valid window.

Unavailable recovery, backup, repository, certificate and DB infrastructure
producers stay explicitly unavailable in this slice. Recovery unknown/unavailable
does not satisfy the accepted recoverability gate; the operator guide preserves
the existing critical/breached policy. No synthetic fixture makes a deployed
measurement available. Future producers retain accepted observation cadence,
thresholds and independently specified evidence windows.

State transitions produce at most one eligible fixed `observation.state` event per actual change. Initial valid observation uses `observed`; fresh success after failed/stale uses `recovered`. Same-state retries do not create transition rows. A separate fixed `observation.threshold` event reports actual crossings of accepted cleanup/pending-deletion warning, critical and breach thresholds, and their clearance, even when availability stays unchanged. Its outcome is `observed` for a threshold crossing and `recovered` for clearance; its reason is `warning`, `critical`, `breach` or `none`. It carries no periodic numeric gauge. Accepted cleanup thresholds are >1 hour warning, 12 hours critical and 24 hours breach; pending deletion is 15 minutes warning, 1 hour or 80% of 1,024 critical. Required unavailable recovery observations do not satisfy their existing release gate. Dependency request failures are eligible for bounded failure rows. Unchanged observation state does not emit a recurring row. Recovery means a fresh successful observation; it never means a
specific client's reconnection or delivery was proven.

## Reviewed examples

Authentication succeeding followed by reservation refusal must be distinguishable.
The stock reservation callback shows `transport: unknown` and omits `session_id`
because it cannot reliably correlate the result. The prototype also shows
100 credential refusals, a blocked writer, failed/stale/recovered sampling, an
uncertain administrator commit, and idle time without a heartbeat.

The HTML is a small simulation of policy, not a production implementation. Its complete simulated-input counts are explanatory demo state, not a promised production counter. Implementation and acceptance cover the agreed logging catalog and limits. The earlier metric proposal is superseded by the human scope correction.
